# medcheck — 원티드 AI Championship 2026 제출

> 제출 화면 항목을 몰라 항목별로 짧게 썼다. 폼이면 그대로 붙여넣고,
> 파일이면 이어붙이면 된다.
>
> 이 문서의 모든 수치는 실측이다. 출처를 댈 수 없는 숫자는 넣지 않았다.
> 재현할 수 없게 된 측정은 그 사실을 적고 뺐다.

## 1. 해결하려는 문제

부모님이 여러 병원에서 약을 받아 오십니다. 내과에서 하나, 정형외과에서
하나, 이비인후과에서 하나. 봉투가 서너 개가 되고, 그 안에 든 약이 서로
겹치는지 아무도 모릅니다.

**의사도 모릅니다.** 각 병원은 자기가 처방한 약만 압니다. 환자가
"다른 데서 뭐 드세요?"라는 질문에 답할 수 있어야 하는데, 70대 어르신이
약 이름 여섯 개를 외워서 말하기는 어렵습니다.

**보호자도 모릅니다.** 약봉투를 들고 가도 이름만 적혀 있지 그게 무슨
약인지, 겹치는지는 알 수 없습니다.

그래서 실제로 이런 일이 일어납니다.

- 같은 성분이 두 봉투에 들어 있어 용량이 두 배가 됨
- 항콜린 작용이 있는 약이 여러 개 겹쳐 인지 기능 저하 위험이 누적됨
- 65세 이상에게 주의가 필요한 약을 본인도 보호자도 모르고 복용

**medcheck는 약봉투를 사진 찍으면 이 셋을 찾아, 진료 때 의사에게
물어볼 문장으로 바꿔 줍니다.**

진단하지 않습니다. 복용을 중단하라고 하지 않습니다.
**"이걸 여쭤보세요"까지만 합니다.** 판단은 의사가 합니다.

## 2. AI 활용 방식

### 쓴 곳과 안 쓴 곳

```
사진에서 글자 읽기    딥러닝 OCR      사람이 대신 못 하는 일
약 이름 찾기         문자열 알고리즘   AI 아님
상호작용 판정         데이터베이스 조회  AI 아님. 결정론이어야 함
질문 문장 다듬기      LLM            없어도 동작함
```

**판정에 LLM을 쓰지 않은 것이 이 설계의 핵심입니다.**

복약 안전 판정은 같은 입력에 항상 같은 답이 나와야 합니다. 어제
"겹칩니다"라고 한 약이 오늘 "괜찮습니다"가 되면 안 됩니다. 그래서
식약처 DUR 데이터를 로컬에 적재하고 규칙으로 조회합니다.

LLM은 마지막 단계에서 문장만 다듬습니다. 그마저도 검증 게이트를 통과
못 하면 원래 문장이 나갑니다.

- 약 이름은 기호로 가려서 보냅니다
- 숫자가 바뀌거나 "중단하세요" 같은 표현이 들어오면 버립니다
- 호출이 실패해도 결과는 나옵니다

### 확신하지 못하면 사람에게 묻는다

약 이름 매칭 결과를 세 등급으로 나눕니다.

```
자동 확정   확신이 높고 2등과 차이가 뚜렷함     체크된 상태로 표시
골라주세요   후보는 있으나 확신이 부족함        사용자가 고름
못 찾음     기준 미달                       검사에서 제외
```

**틀린 약을 자신 있게 확정하는 것을 가장 위험한 실패로 정의했습니다.**
못 찾은 약은 사용자가 화면에서 알 수 있지만, 틀리게 확정된 약은 모른 채
의사에게 말하게 됩니다.

실물 약봉투 10장 55개 약에서 **틀린 약을 확정한 경우는 0건**입니다.

### 2단 카탈로그

식약처 DUR 데이터는 상호작용 정보가 있는 약만 담습니다. 그런데 실제
약봉투에 적힌 약의 **상당수가 그 밖에** 있었습니다. 정장제, 유산균,
일반의약품이 그렇습니다.

없으면 화면에 안 뜨거나, 더 나쁘게는 이름이 비슷한 다른 약이 대신
뜹니다.

그래서 인식용 카탈로그를 따로 얹었습니다.

```
1단  DUR 카탈로그   19,441품목   판정까지 감
2단  허가 목록      46,554품목   이름만 맞히고 "확인 대상 정보 없음"으로 표시
                              이 중 27,113품목은 2단에만 있음
```

**"못 읽었다"와 "읽었는데 볼 정보가 없다"는 사용자에게 완전히 다릅니다.**

## 3. 사용한 AI 도구

```
PaddleOCR (PP-OCRv4 한국어)   딥러닝 OCR. 검출(DBNet) + 인식(CRNN 계열)
                             ONNX로 변환해 서버에서 직접 추론
Claude (Anthropic)           질문 문장 다듬기. 없어도 동작
```

**둘뿐입니다. 그리고 그게 의도입니다.**

AI를 더 넣어봤고, 측정해서 뺐습니다. 아래 세 가지는 실패가 아니라
**측정해서 기각한 가설**입니다.

### 기각한 가설 셋

**OCR 신뢰도로 오탐을 거르려 했습니다.**
```
정답으로 매칭된 줄   신뢰도 중앙 0.989
오탐으로 매칭된 줄   신뢰도 중앙 0.995
```
**오탐의 신뢰도가 더 높았습니다.** OCR은 뭉갠 글자를 자신 있게 읽습니다.
임계를 어디에 걸어도 오탐보다 정답이 먼저 죽습니다.
**기계가 자기 확신을 못 믿는다는 것이 사람 확인 화면이 필수인 이유입니다.**

**OCR 엔진 두 개를 병행해 상호 보완하려 했습니다.**
합집합이 단독 대비 늘지 않았습니다. 같은 모델을 런타임만 바꿔 돌린
것이라 두 엔진이 같은 글자에서 같이 틀렸습니다. **"두 개를 쓰면 낫다"는
직관이 모델이 같으면 성립하지 않습니다.**

**최신 세대 모델로 교체하려 했습니다.**
같은 사진, 같은 조건에서 **PP-OCRv5가 PP-OCRv4보다 4건 적게 찾았습니다.**
범용 벤치마크에서는 v5가 크게 앞섭니다. 도메인 데이터에서 재현되지
않았습니다.

> 이 A/B의 절대 수치는 문서에 싣지 않았습니다. 당시 비교용으로 조립한
> 실행 설정이 배포본과 달라(전처리 옵션 세 개 누락) 두 팔 모두 실제보다
> 낮게 나왔기 때문입니다. **두 팔이 같은 조건이라 "v5가 4건 적다"는
> 방향은 유효하지만, 절대 수치는 시스템 성능이 아닙니다.** 같은 이유로
> 이 비교에서 나온 속도 수치도 쓰지 않았습니다.

## 4. 측정

실물 약봉투 10장, 55개 약. 정답은 봉투 인쇄를 사람이 옮겨 적은 것입니다.

```
약 이름 찾음      45개  81.8%
자동 확정        33개  60.0%
틀린 약 확정       0개
```

**판정 기준은 정답 이름의 앞 4글자 일치입니다.** 앞 3글자로 재면
47개(85.5%)가 나옵니다. 기준을 적지 않으면 어느 쪽인지 알 수 없어
같이 씁니다.

### 정답지 자체에 오류가 있었습니다

정답지는 사람이 봉투 인쇄를 옮겨 적은 것입니다. 검증 과정에서 **확인된
오류 2건, 미확인 2건**이 나왔습니다.

```
확인   시스템이 맞게 찾았는데 정답지가 틀려 오답으로 집계된 것   2건
미확인  같은 유형으로 의심되나 원본 사진 재확인이 필요한 것      2건
```

**정답지를 고쳐서 점수를 올리지 않았습니다.** 우리에게 유리한 방향으로
정답을 고치는 것이기 때문입니다. 45/55를 그대로 두고 이 사실을 같이
적습니다. 확인된 1건을 반영하면 46/55(83.6%)가 됩니다.

### 못 찾은 10건의 원인

카탈로그 전수 조회와 실제 OCR 출력을 대조해 분류했습니다.

```
정답지 오류        1건   시스템은 맞게 확정했으나 정답지가 틀림
정답지 오류 의심    1건   원본 사진 재확인 필요
OCR 오독·미검출    4건   글자를 잘못 읽거나 줄 자체를 못 찾음
카탈로그 미등재     3건   공개 API 범위 밖
매칭 실패         1건   OCR은 맞게 읽었으나 다른 약이 1위
```

**순수한 매칭 실패는 1건입니다.** `클락신정`을 정확히 읽었는데
`클리신정`이 이겼습니다. 나머지는 매칭 앞이나 데이터 쪽 문제입니다.

OCR 오독 4건 중 `뮤테란캅셀`은 5.1에서 고친 표기 정규화가 이미 커버하는
건입니다. 글자만 제대로 읽혔으면 붙었습니다.

### 처리 시간

배포 서버(AWS t3.small, 서울)에서 실물 사진으로 측정했습니다.
캐시가 비어 있는 첫 요청 기준입니다.

```
사진               개선 전    개선 후
약봉투 (42줄)       25.2s  ->  20.4s   -19%
약봉투 (33줄)       28.3s  ->  19.9s   -30%
약국 영수증 (129줄)  90.6s  ->  58.1s   -36%
```

**걸리는 시간은 검출된 글자 줄 수에 거의 비례합니다.** 129줄짜리는
약봉투가 아니라 약국 영수증이었습니다.

업로드 응답 자체는 **58초에서 0.1~0.3초**가 되었습니다(5절 참조).

## 5. 시행착오

**이 절이 이 프로젝트에서 가장 시간을 많이 쓴 부분입니다.**

### 5.1 정확도 — 24개 중 11개에서 55개 중 45개로

처음 실물 사진을 넣었을 때 24개 중 11개였습니다. 무엇이 문제인지
하나씩 분리했습니다.

**긴 이름이 짧은 오답에 졌습니다.** 카탈로그 이름이 `제품명(성분명)`
형태라 성분명이 길수록 길이 비율로 점수가 깎였습니다.

```
OCR 줄   애니크라정375밀리그램아목
정답     애니크라정375밀리그램(아목시실린수화물-…)   37자   83.6
오답     유니크라정375밀리그램                    12자   84.6
```

내용은 정답이 훨씬 가까운데 길이 때문에 집니다. 괄호 앞까지만 잘라서도
한 번 재고 높은 쪽을 쓰도록 했습니다. 92.3 대 84.6으로 뒤집혔습니다.

**같은 말인데 표기가 갈렸습니다.** 봉투에 `뮤테란캅셀`로 인쇄된 약이
`뮤테란과립`(다른 제형)에 67.5점으로 붙고 있었습니다. 카탈로그에
`캡슐` 9,358건과 `캅셀` 278건이 **둘 다 실재**했습니다(1단·2단 합계
65,995품목 기준). 소수파를 주류로 정규화하니 정답이 90.0점으로 1위가
되었습니다.

**허가 취하된 품목을 걸러내고 있었습니다.** 봉투에 인쇄된 약이
카탈로그에 없다고 나오길래 이름을 검색해 보니 실제로 존재하는 약이었고,
취하 상태라 우리가 적재 단계에서 버리고 있었습니다. **약은 취하돼도
사람의 서랍에는 남아 있습니다.**

**임계값은 건드리지 않았습니다.** 자동 확정 기준은 합성 데이터 시절에
정한 뒤 바꾸지 않았습니다. 실물 55건으로 재조정하면 숫자는 올라가지만
검증할 홀드아웃이 없어 과적합을 구분할 수 없습니다. **하지 않은 이유를
같이 적습니다.**

### 5.2 지연 — 매칭이 아니라 매칭 밖에 있었습니다

정확도 작업을 닫은 뒤 속도를 봤습니다. 사진 한 장이 25~91초였습니다.

**카탈로그 이름을 질의마다 다시 가공하고 있었습니다.** 약 이름 하나를
찾을 때마다 46,554개 문자열을 두 번씩 재가공했습니다. 약 네 개면
37만 번입니다. 프로세스 기동 시 한 번만 하도록 바꿨습니다.

**버릴 후보를 계속 고르고 있었습니다.** 1단 결과가 이미 충분히 높을
때도 2단 검색을 문턱 없이 돌았습니다. 어차피 버릴 점수대를 검색
라이브러리에 미리 알려주자 내부에서 가지치기가 일어났습니다.

두 가지를 합쳐 매칭이 **1.54배** 빨라졌습니다(로컬 질의 621개 기준,
원격 실물 1.52~1.53배로 재현). **질의 621개를 변경 전후로 돌려 확정 약,
상태, 후보 목록, 점수까지 전부 대조해 불일치 0을 확인한 뒤 적용했습니다.**
속도 때문에 답이 바뀌면 안 되기 때문입니다.

**매칭이 서버 전체를 멈추고 있었습니다.** 129줄 사진의 매칭 45초 동안
`/health`를 포함해 **어떤 요청에도 응답하지 않았습니다.** 컨테이너
헬스체크가 30초 간격 3회라, 긴 요청 두 건이면 컨테이너가 비정상으로
넘어갑니다. 별도 스레드로 분리해 업로드 중에도 다른 요청이 12~55ms에
응답하는 것을 확인했습니다.

**쓰레기 줄을 먼저 버리는 게 더 컸습니다.** 영수증에는 승인번호,
사업자번호, 약효분류 라벨이 섞여 있습니다. 이런 줄을 걸러내자 매칭이
**34~47%** 더 줄었습니다. 없어지는 줄이 하필 위 가지치기가 듣지 않는
줄이라, 두 최적화가 서로 다른 줄을 공략했습니다.

이 필터는 **카탈로그 65,995건 전체로 검증**했습니다. 실제 품목명을
하나라도 죽이는 규칙은 채택하지 않았습니다. 규칙 하나는 실제 품목
21건을 죽여서 버렸습니다. 예외 목록을 늘려 살릴 수 있었으나 그러면
우리 사진에 맞추는 것이 됩니다.

### 5.3 근거 없이 쓰던 설정을 측정했습니다

OCR 스레드 수를 2로 쓰고 있었는데, 그 값은 24코어 개발 머신에서 잰
것이었습니다. 배포 서버는 물리 코어가 하나입니다.

```
스레드    약봉투(42줄)   영수증(129줄)   약봉투(33줄)     조건당 1회
1         24.2s         66.1s          21.5s
2 (현행)   13.6s         39.1s          13.8s
4         21.0s         67.3s          22.6s
```

**설정은 바뀌지 않았습니다. 근거가 생겼습니다.** 1은 vCPU를 놀리고
4는 문맥 전환으로 까먹습니다.

같은 방식으로 동시 처리도 쟀습니다. 아래는 위 지연 개선을 적용하기 전
빌드에서 잰 것이라 단건 절대값이 지금(약 20초)보다 큽니다. 서로를
비교하는 표라 결론은 그대로 유효합니다.

```
동시 1건   1건 / 24.2s = 0.041 req/s
동시 2건   2건 / 51.3s = 0.039 req/s
동시 3건   3건 / 72.0s = 0.042 req/s
```

**처리량이 평평합니다.** 동시에 받아도 초당 처리량은 그대로고 모든
사용자의 대기시간만 세 배가 됩니다. 그래서 병렬로 돌리지 않고 줄을
세웁니다.

### 5.4 정확도만 재고 그 뒤를 아무도 안 봤습니다

**이 프로젝트에서 가장 값비싼 교훈입니다.**

45/55라는 숫자는 약 이름을 찾는 단계까지만 잰 것이었습니다. 그 뒤
단계는 아무도 측정하지 않았고, 거기서 두 개가 나왔습니다.

**확정한 약의 절반이 결과 화면에서 사라졌습니다.** 2단 카탈로그에서
확정된 약이 결과를 만들 때 조용히 빠졌습니다. 오류도 경고도 없습니다.

```
실물 13장 자동 확정 43건 = 1단 23건 / 2단 20건   →  47%가 소실
```

봉투 한 장이 전부 2단 약이면 "0개 약"이 뜨고 브리핑이 통째로 빕니다.
설계는 "2단은 이름만 맞히고 판정은 못 한다"였는데, 코드가 **"판정을
못 한다"를 "목록에서 지운다"로 구현**하고 있었습니다.

**없는 소견을 만들어내고 있었습니다.** 영수증에는 같은 약이 표와
설명란에 두 번 인쇄됩니다. OCR이 두 줄로 읽고 매칭이 **둘 다 정확히
같은 약으로 맞히면**, 사용자가 둘 다 체크합니다.

```
화면 출력   항콜린 부담 합계가 4점입니다 (검토 권장 3점 이상)
              2점 시메티딘 — 싸이메트정(시메티딘)
              2점 시메티딘 — 싸이메트정(시메티딘)
```

같은 약 한 종이라 실제는 2점이고 권장 기준 아래입니다. **매칭이 잘
동작해서 생긴 버그**라 매칭 쪽에서는 고칠 수 없었습니다. 집계 단계에서
봉투별로 접었습니다. 봉투가 다르면 접지 않습니다 — 다른 병원에서 같은
약을 받은 것을 찾아내는 것이 이 도구의 목적입니다.

**둘 다 정확도 작업을 닫은 뒤에 나왔고, 둘 다 매칭 밖에 있었습니다.**
지표를 자기 담당 단계까지만 재면 그 뒤는 보이지 않습니다.

### 5.5 검증 입력을 스스로 고르면 안 됩니다

직접 입력 자동완성을 만들고 스스로 테스트해서 통과시켰습니다. 실물
약봉투에 인쇄된 이름으로 다시 재니 **10개 중 8개가 후보에 아예
없었습니다.**

```
액티피드시럽 → 큐피시럽      위피드정 → 피드로정
에리우스정   → 에이리스정    킨도라제정 → 도라셋정
```

사용자는 자기 약이 없고 남의 약 여섯 개를 봅니다. 사진 경로는 같은
이름을 정확히 찾는데 자동완성만 못 찾았습니다.

**자체 검증이 통과한 이유가 문제였습니다.** 테스트에 쓴 이름이 하필
우연히 통과하던 유일한 경우였고, **그 이름을 만든 쪽이 직접 골랐기
때문**입니다. 고친 뒤에는 카탈로그에서 무작위로 뽑은 20개로 다시
쟀습니다(20/20 1위).

### 5.6 배포 절차를 관객 없을 때 먼저 깨봤습니다

무중단 교체 스크립트를 만들고, 아무도 보지 않는 시점에 실행했습니다.
**세 번 깨졌고 그중 한 번은 서비스를 실제로 내렸습니다.**

```
1  컨테이너 이름만 바꾸고 새것을 띄웠다. 포트가 안 비워진다   안전하게 실패
2  존재 확인 명령이 컨테이너와 이미지를 둘 다 본다.
   이미지 이름이 같아서 가드가 뚫렸고 돌던 서비스를 지웠다   서비스 다운
3  Windows에서 편집해 줄바꿈이 섞여 스크립트가 깨졌다        안전하게 실패
```

다운타임은 1~2분이었고 사용자는 0명이었습니다. **심사 기간 중에 급히
고칠 일이 생겼다면 이 스크립트를 그때 처음 돌렸을 것입니다.** 지금은
빌드를 먼저 끝내고 성공했을 때만 교체하며, 실패하면 이전 컨테이너로
되돌아갑니다. 교체 다운타임은 약 10초입니다.

### 5.7 사진을 보내고 기다리는 구조를 버렸습니다

사진 한 장이 20~58초인데, 그동안 요청 하나가 계속 열려 있었습니다.
**폰 화면이 꺼지면 연결이 끊기고 서버가 한 일이 전부 버려집니다.**
사용자는 처음부터 다시 찍어야 합니다. 이 도구의 사용자는 약국 앞에 서
있는 사람이라 그 상황이 예외가 아니라 기본입니다.

접수번호를 먼저 돌려주고 브라우저가 주기적으로 물어보는 방식으로
바꿨습니다.

```
업로드 응답     58초  ->  0.1~0.3초
화면을 닫아도   서버는 계속 읽음. 주소를 다시 열면 결과가 있음
```

여기서 세 가지를 같이 처리했습니다.

**접수번호가 곧 열쇠입니다.** 로그인이 없으므로 번호를 아는 사람이 그
사람의 복약 목록을 봅니다. 추측할 수 없는 128비트로 발급하고, 로그에는
앞 6자만 남기고, 외부로 새지 않도록 리퍼러 정책을 서버가 직접
지정합니다.

**떠난 사람이 남은 사람을 막지 않게.** 탭을 닫아도 작업은 돕니다.
작업자가 하나뿐이라 유령 작업 하나가 뒤의 진짜 사용자를 58초 막습니다.
폴링이 살아있음 신호를 겸하도록 하고, 차례가 왔는데 소식이 없으면
일하지 않고 버립니다.

**대기시간을 과소 약속하지 않게.** 처음에는 흔한 쪽(20초)으로
추정했는데, 영수증이 네 장 몰리면 "75초"라고 말하고 실제로는 175초가
걸렸습니다. 관측 상한 쪽으로 올리고 화면에는 단일 숫자 대신 범위로
적습니다. **덜 기다리면 기분이 좋고 더 기다리면 고장으로 보입니다.**

### 5.8 진행 막대를 가짜로 채우지 않았습니다

40초 동안 화면이 멈춰 있으면 사용자는 고장으로 읽습니다. 그런데 서버가
몇 퍼센트를 했는지 브라우저는 알 수 없습니다.

그래서 막대를 **작업 진행률이 아니라 예상 시간 대비 경과**로 정의하고,
응답이 오기 전에는 100%에 닿지 않게 했습니다.

```
예상 시간   90%
2배 경과    95.7%
5배 경과    98.8%
```

다 됐다고 거짓말하지 않습니다. 예상의 1.5배를 넘기면 "멈춘 것이
아닙니다"로 문구가 바뀝니다.

## 6. 사람이 찾은 문제

**아래는 AI 도구가 찾지 못하고 만든 사람이 찾은 것들입니다.**

이 프로젝트는 설계, 구현, 측정, 문서까지 AI 도구를 적극적으로
썼습니다. 그런데 **중요한 방향 전환은 대부분 사람이 만들었습니다.**
공통점이 있어 따로 적습니다.

### 6.1 "그거 오타일 수도 있지 않나"

`뮤테란캅셀`이 카탈로그에 없다고 처리되고 있었습니다. 만든 사람이
약품 설명에서 "흰색의 캡슐제"를 보고 표기 차이를 의심했습니다.

카탈로그에는 `캡슐` 9,358건과 `캅셀` 278건이 **둘 다 실재**했습니다
(1단·2단 합계 65,995품목 기준).
AI 도구는 "카탈로그에 없다"를 데이터의 사실로 받아들였고, 사람은
"인쇄가 다를 수 있다"를 의심했습니다.

### 6.2 "못 찾은 목록을 검색해서 실제로 있는 약인지 확인했나"

확인하지 않았습니다. 검색해 보니 실재하는 약이었고, 허가 취하 품목을
적재 단계에서 버리던 버그가 드러났습니다.

**AI 도구는 자기 파이프라인 안에서만 확인했습니다.** 바깥 세계에 물어
보라는 지시가 사람에게서 나왔습니다.

### 6.3 정답지 자체를 의심했습니다

시스템이 틀렸다고 보고한 항목을 사람이 원본과 대조해, **정답지가 틀린
경우**를 찾아냈습니다. 측정의 기준선을 의심하는 일은 그 기준선으로
점수를 받는 쪽이 하기 어렵습니다.

### 6.4 "브리핑이 안 뜬다"

사용자로서 화면을 보고 한 말이었습니다. AI 도구 둘 다 이를 문장 다듬기
단계의 문제로 설명하고 넘어갔습니다. 실제 원인은 **확정한 약의 47%가
결과에서 사라지던 버그**였을 가능성이 높습니다(추정입니다. 당시 화면을
재현하지 못해 확정하지 못했습니다).

**사용자가 본 것을 가설로 설명하고 확인하지 않은 것**이 그 자체로
같은 종류의 실수였습니다.

### 6.5 "이거 PC 프로그램이잖냐"

AI 도구는 PC 브라우저로만 확인하고 있었습니다. 실제 사용자는 약국
앞에서 폰으로 찍습니다. 지적을 받고 모바일 경로를 점검해, 입력칸을
누를 때마다 화면이 확대되는 문제를 찾았습니다.

### 6.6 "약마다 칸을 나누면 어떨까"

직접 입력이 한 칸에 여러 줄을 적는 방식이었습니다. 만든 사람이 약마다
칸을 나누는 구조를 제안했고, **그 구조가 자동완성을 붙일 수 있게 한
전제**였습니다. 한 칸에 여러 줄이면 어느 줄을 완성해줄지 알 수 없습니다.

자동완성이 붙자 오탈자와 용량 표기 차이가 **원천적으로 사라졌습니다.**
사용자가 친 글자가 아니라 고른 품목코드가 넘어가기 때문입니다.

### 6.7 "1분이면 휴대폰 절전이 되고도 남는다"

처리 시간을 줄이는 쪽만 보고 있었습니다. 만든 사람이 **시간을 못 줄여도
안 죽게 만드는 길**을 지적했고, 그것이 5.7의 구조 변경이 되었습니다.

속도 최적화로는 58초를 30초로 만드는 것이 한계였고, 30초도 화면이
꺼지기에 충분합니다. **문제를 다시 정의한 쪽이 사람이었습니다.**

### 이 절에서 말하려는 것

일곱 건의 공통점은 **AI 도구가 자기 측정 범위 안에서는 모두 통과했다는
것**입니다. 테스트는 통과했고, 지표는 좋았고, 로그에 오류가 없었습니다.

- 자기가 고른 입력으로 검증하면 통과합니다
- 자기 담당 단계까지만 재면 그 뒤는 안 보입니다
- 사용자가 본 것을 자기 가설로 설명하면 확인이 끝나 버립니다

**사람이 한 일은 코드를 쓰는 것이 아니라 측정의 경계를 의심하는
것이었습니다.** 이 프로젝트에서 AI 도구의 생산성이 실제로 높았기
때문에, 그 경계를 누가 지키는지가 더 중요해졌습니다.

## 7. 한계

**공개 API 범위** — 식약처 공개 API가 주는 정보로 46,554품목을
구성했습니다. 식약처 웹 데이터베이스에는 더 있으나 공개 API로는 받을
수 없습니다. 실물 측정에서 이 범위 밖인 약이 있었습니다.

**표본 크기** — 실물 약봉투 10장, 55개 약입니다. 이 숫자로 일반화하지
않습니다. 정답지에도 확인된 오류 2건과 미확인 2건이 있습니다.

**임계값** — 자동 확정 기준을 실물 데이터로 재조정하지 않았습니다.
검증할 홀드아웃이 없어 과적합과 개선을 구분할 수 없기 때문입니다.

**판정 범위** — DUR 데이터에 등재된 상호작용만 봅니다. 등재되지 않은
조합은 찾지 못합니다. 그래서 확인할 내용이 없을 때도 "문제 없음"이라고
하지 않고 **"발견되지 않았습니다"**라고 씁니다.

**처리 시간** — 사진 한 장에 20~58초입니다. 대부분이 OCR이고, 걸리는
시간은 글자 줄 수에 거의 비례합니다. 더 빠른 한국어 모델은 정확도가
떨어져 채택하지 않았고, 더 큰 서버는 문제의 성격을 바꾸지 못합니다
(30초도 화면이 꺼지기에 충분합니다). **속도 자체는 남은 과제입니다.**
지금은 시간을 줄이는 대신 **기다리는 동안 안 죽게** 만들었습니다.

**단일 프로세스 전제** — 접수번호를 메모리에 들고 있어 서버 프로세스를
여러 개로 늘리면 동작하지 않습니다. 현재 규모에서는 문제가 아니지만,
확장 시 먼저 바꿔야 하는 지점입니다.

## 8. 기술 구성

```
웹          FastAPI + Jinja2
OCR         PaddleOCR 한국어 모델을 ONNX로 변환, onnxruntime으로 추론
매칭        rapidfuzz. 품목 4만6천건을 메모리에 적재
데이터       SQLite. 식약처 DUR + 허가목록 + 항콜린 척도(KABS)
배포        Docker 단일 이미지, AWS EC2. 외부 API 의존 없음
테스트       171개
```

**사진과 약 이름이 서버 밖으로 나가지 않습니다.** OCR을 클라우드 API로
돌리면 더 정확하지만, 약봉투에는 환자 이름과 생년월일이 찍혀 있습니다.
문장 다듬기에 외부 LLM을 쓸 때도 약 이름은 기호로 가려서 보냅니다.
